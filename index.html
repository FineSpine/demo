Requirements: requirements.txt (Incident Management Service)
Last updated: 2026-11-06 11:09 UTC

a) What is right

  • The getIncidentId() compile error in RespondentService is fixed: Respondent now has a service field and the lookup uses it.
  • IncidentManagerService logs the created incident with id, service, and severity, which is useful for tracing.
  • WebController logs the alert fields at info level.

b) What is wrong

  • IncidentManagerService.incidentsById is still never initialized, so registerIncident throws a NullPointerException.
  • IncidentManagerService.registerIncident: the duplicate-id branch is still empty.
  • IncidentManagerService.getAndRegisterIncidentFromAlert: severity is still derived from the service name ("payments", "login"), not from the alert. Also, if neither matches, severity stays INFO only by accident of the constructor.
  • WebController.accept only logs. It never calls getAndRegisterIncidentFromAlert, NotificationService, or RespondentService, so no incident is created on intake.
  • RespondentService is not called from anywhere, and findRespondentByIncident matches by service only, not by category as the spec requires.
  • Respondent still lacks category(), noteAcknowledgement(), and getNextRespondent().
  • NotificationService: import org.persistence.Main is still unused.

c) What to do next

  1. Must-have (runtime): initialize the map: private final TreeMap<String, Incident> incidentsById = new TreeMap<>();
  2. Must-have: in WebController.accept, call the manager, then the notifier: 
    Incident incident = incidentManagerService.getAndRegisterIncidentFromAlert(alert);
notificationService.sendNotification(incident);
  3. Must-have: derive severity from the alert with a function instead of contains("payments").
  4. Should-have: call RespondentService.findRespondentByIncident from the same flow, and add a category to Respondent.
  5. Cleanup: remove the unused Main import from NotificationService and throw on duplicate ids.
