Requirements: requirements.txt (Incident Management Service: alert intake, incident creation, severity-based actions)
Last updated: 2026-11-06 10:45 UTC

a) What is right

  • Alert has the four fields from the spec (serviceName, serviceId, errorMessage, reportedApi).
  • IncidentSeverity covers the three severities; the spec names warning, the enum uses WARN, which is fine if consistent.
  • WebController.accept takes an Alert and returns an acknowledgement, matching the "ack on receipt" step.

b) What is wrong

  • Incident and IncidentManagerService are empty. Incident creation, severity routing, and storage are not implemented yet.
  • WebController.accept only logs and acks. It must create an incident from the alert and hand it to the manager.
  • WebController.accept: ResponseEntity<?> and string concatenation in the log call. Use ResponseEntity<AlertAcknowledgement> and log.debug("...{}", alert).
  • Responder (spec entity) and the severity actions (phone for CRITICAL, email for WARN, no-op for INFO) are missing.
  • ExternalApiService and getResource are unrelated to the spec. They can stay if the email/phone dummies will use them, otherwise remove them.
  • Alert is missing the spec's behaviour of a rogue-service/duplicate-ack path; for now, keep it a plain DTO.

c) What to do next

  1. Must-have: build Incident (id, serviceName, serviceId, errorMessage, reportedApi, severity, createdAt) and a severity function such as IncidentSeverity getSeverityFromAlert(Alert a) in IncidentManagerService.
  2. Must-have: in accept, create the incident, store it, and dispatch by severity: 
    public class IncidentManagerService {
    public Incident createIncident(Alert alert) { ... }
    public void act(Incident incident) {
        switch (incident.getSeverity()) {
            case CRITICAL -> call(incident);   // dummy phone
            case WARN     -> email(incident);  // dummy email
            case INFO     -> { }              // no-op
        }
    }
}
  3. Should-have: add a Responder class with category() and getNextRespondent() stubs, called from the dispatch.
  4. Should-have: storage. A TreeMap<String, Incident> keyed by id is enough; add a date/service filter method on it.
  5. Cleanup: remove unused ResourceBundle import (if still present), remove the Lombok-only AlertAcknowledgement in favour of a record, and delete ExternalApiService if no dummy call uses it.
