Requirements: requirements.txt (Incident Management Service)
Last updated: 2026-11-06 11:13 UTC

a) What is right

  • incidentsById is now initialized, so registerIncident no longer throws.
  • WebController now creates the incident via IncidentManagerService and looks up a respondent, which wires intake to the core flow.
  • Constructor injection in WebController is clean and testable.

b) What is wrong

  • WebController.accept never calls NotificationService.sendNotification. The spec's core step (act on the incident by severity) is missing from intake.
  • NotificationService is not a Spring bean (no @Service), so it cannot be injected into the controller until it is annotated.
  • IncidentManagerService.getAndRegisterIncidentFromAlert: severity is still derived from contains("payments") and contains("login"), not from the alert. Also, the second if can overwrite the first.
  • IncidentManagerService.registerIncident: the duplicate-id branch is still empty. Throw an exception there.
  • Respondent still lacks category(), noteAcknowledgement(), and getNextRespondent(), and findRespondentByIncident matches by service only.

c) What to do next

  1. Must-have: inject NotificationService into WebController and call it after the incident is created. Annotate NotificationService with @Service: 
    Incident incident = incidentManagerService.getAndRegisterIncidentFromAlert(alert);
notificationService.sendNotification(incident);
  2. Must-have: replace contains(...) severity logic with a single function on the alert, e.g. IncidentSeverity getSeverityFromAlert(Alert alert), with an explicit INFO default.
  3. Should-have: throw on duplicate ids in registerIncident.
  4. Should-have: add a category to Respondent and let findRespondentByIncident match by category.
