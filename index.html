3c. Next priority: state model and validation

Build the model first. The spec is a per-client counter that resets on epoch-aligned windows, so the core entity is a small state record holding windowId and count. Define it and the constructor validation before writing allow. This matches the required API (maxRequests, windowSizeMillis, allow(clientId, timestampMillis)) and keeps the rules testable from the start.

Suggested skeleton (not an implementation):

public final class FixedWindowRateLimiter {
    private static final class WindowState {
        final long windowId;
        int count;
        WindowState(long windowId, int count) { this.windowId = windowId; this.count = count; }
    }

    private final int maxRequests;
    private final long windowSizeMillis;
    private final Map<String, WindowState> states = new HashMap<>();

    public FixedWindowRateLimiter(int maxRequests, long windowSizeMillis) {
        if (maxRequests <= 0 || windowSizeMillis <= 0)
            throw new IllegalArgumentException("maxRequests and windowSizeMillis must be > 0");
        this.maxRequests = maxRequests;
        this.windowSizeMillis = windowSizeMillis;
    }

    public boolean allow(String clientId, long timestampMillis) { /* validate, then core logic */ }
}

Pitfalls to avoid:

  • Compute the window as timestampMillis / windowSizeMillis (integer division). Do not reset based on the client's first request time; that breaks epoch alignment.
  • A rejected request must not increment the stored count. Check count >= maxRequests before incrementing.
