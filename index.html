Requirements: requirements.txt (Incident Management Service)
Last updated: 2026-11-06 10:53 UTC

a) What is right

  • Incident carries severity, id, service, and createdAt, which matches the spec's indexing fields (date, service, severity).
  • IncidentManagerService.registerIncident keys the store by incident id, which fits the TreeMap<id, Incident> design.
  • IncidentSeverity and Alert are in place from the earlier cycle.

b) What is wrong

  • IncidentManagerService.getIncidentFromAlert: if() has no condition. This is a compile error; the method also never sets severity or copies alert fields into the incident.
  • IncidentManagerService.incidentsById is never initialized. registerIncident will throw a NullPointerException.
  • IncidentManagerService.registerIncident: the duplicate-id branch is empty. Throw on duplicates, or document why not.
  • Incident: a hand-written no-args constructor plus @NoArgsConstructor and @AllArgsConstructor is redundant, and the defaults (INFO, empty service) overwrite what the factory sets. Use one constructor and let the service populate it.
  • Incident lacks the alert fields (serviceName, serviceId, errorMessage, reportedApi) that the spec requires for the incident.
  • WebController.accept still only logs and returns an ack. It does not call the manager, so no incident is created.
  • WebController.accept: ResponseEntity<?> and string concatenation in the log call; use ResponseEntity<AlertAcknowledgement> and log.debug("...{}", alert).
  • Severity routing (CRITICAL call, WARN email, INFO no-op) is not implemented anywhere yet.

c) What to do next

  1. Must-have (compile): fix the if() and initialize the map: 
    private final TreeMap<String, Incident> incidentsById = new TreeMap<>();
  2. Must-have: complete the factory. Set severity from getSeverityFromAlert(alert) and copy the alert fields onto the incident: 
    public Incident getIncidentFromAlert(Alert alert) {
    Incident incident = new Incident(...);  // populate severity, service, alert fields
    return incident;
}
  3. Must-have: wire the controller. Call getIncidentFromAlert, then registerIncident, then dispatch by severity.
  4. Should-have: add the severity routing method with the three cases (CRITICAL, WARN, INFO) and dummy call/email bodies.
  5. Should-have: simplify Incident to a single constructor that takes the fields.
  6. Optional: add a Responder stub with category() and getNextRespondent().
