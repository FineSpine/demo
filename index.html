Requirements: requirements.txt (Incident Management Service)
Last updated: 2026-11-06 11:01 UTC

a) What is right

  • NotificationService.sendNotification switches on severity, which is the right shape for the dispatch.
  • Incident has the severity, id, service, and createdAt fields the spec needs for indexing.

b) What is wrong

  • NotificationService.sendNotification: the switch has only the CRITICAL case. WARN (email) and INFO (no-op) are missing, and there is no break, so the CRITICAL case falls through once more cases are added.
  • NotificationService: case IncidentSeverity.CRITICAL: is not valid in an enum switch on Java 21; use case CRITICAL ->.
  • NotificationService: import org.persistence.Main is unused. Remove it.
  • NotificationService is a class, not the interface from the last cycle. Either keep the interface with a dummy impl, or keep the class; pick one and inject it.
  • Incident: @NoArgsConstructor was removed, but the hand-written no-args constructor still exists. Keep the single no-arg constructor, or switch to a single all-args constructor.
  • IncidentManagerService.incidentsById is still never initialized, so registerIncident throws a NullPointerException.
  • IncidentManagerService: severity is still derived from the service name ("payments", "login"), not from the alert.
  • WebController.accept still never calls the manager or the notification service, so no incident is created on intake.

c) What to do next

  1. Must-have (runtime): initialize the map in IncidentManagerService.
  2. Must-have: complete the switch with all three severities and -> arms: 
    switch (incident.getSeverity()) {
    case CRITICAL -> log.info("Dummy phone call");
    case WARN     -> log.info("Dummy email");
    case INFO     -> { }
}
  3. Must-have: call the manager and the notifier from WebController.accept.
  4. Should-have: derive severity from the alert, not the service name.
  5. Cleanup: remove the Main import in NotificationService and the duplicate constructor in Incident.
